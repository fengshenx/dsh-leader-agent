# 协调者手册把 routing 边界写死

**状态**：implemented（2026-11-02）
**范围**：`COORDINATOR.md`、本笔记

## 背景

手册原本写「功能代码交 worker 实现」，把实现面收在一个「代码」字眼上——测试、文档、配置三类改动仍留在协调者手里；紧接着一句「局部问题（读一段代码、答一个疑问、改一行配置）直接处理」又给了自己动手的合法入口。两处叠起来的后果是 PR #37 本身由协调者代写，事后要 worker 接管重做一遍，卡才重新有真实执行者与验证记录。

同一轮还漏了两件事：worker 开出的 PR / Issue 没挂到卡的 `links`（#3 漏 PR #36、#4 漏 PR #35、#6 漏 PR #33），看板上从卡看不到交付物；给常驻 worker 发消息用了 `SendMessage`，恢复时报 `Agent "review-pr33" not found in registry or persisted transcripts`。

## 决策

**协调者只做 routing，不留例外**。手册写成「你只做 routing：目标、拆分、派工、验收、合并与收尾」＋「不亲自落地：代码、测试、文档、配置的改动一律派 worker——没有例外」。理由不是纪律洁癖：协调者亲手改的那一刻，卡的检查点就不再对应真实执行者，验收退化成自己验自己；worker 接手时还得重读一遍才知道自己「交付」了什么。

**「非得自己动手」按拆卡处理**。写死判据而不是例外条款：觉得必须亲手改，说明范围在派工后变了——按新范围记卡、补简报再派。措辞必须无条件：「真需要时」这类限定语一出现，例外就成了可援引的口子，而协调者正是最容易说服自己「这次是例外」的那个人。

**只读判断不算落地**。保留「读一段代码、答一个疑问、比对 diff 与输出」可以直接给结论。判据是**有没有产出改动**，不是事情大小——「改一行配置」曾是允许项，它正是漏进来的第一道口子。

**产出挂卡要带并发校验**。`update_card` 的 `links` 是整体替换（`src/host/cards/store.js:222`，`next.links = links`），只写「先读卡带上已有条目」在跨会话并发下仍会丢条目：两次读-改-写交错时，后写的那次冲掉对方刚挂上的条目。手册因此要求同时带 `expectedRevision`（校验与取值在 `src/host/cards/store.js:207-211`，版本不符即拒写），冲突就重读再写。

**别处已有的规则只留指针**。worker 入口为什么只有 `spawn_worker` / `message_worker`、宿主三件为什么落不到它身上，`AGENTS.md` 核心铁律、`skills/leader-mode/SKILL.md` 与 `playbooks/program.md`「协调者动作与工具」都写过；手册改成一行断言加指针，只保留它独有的参数细节——`cardId`。`SendMessage` 不在这些文档里，协议层没有对应条目，只能在手册直写：指针必须指得到依据，指不到就把那半条留在原地。
