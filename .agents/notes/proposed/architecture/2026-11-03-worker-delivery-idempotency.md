# Agent Note: worker 回报的投递语义：at-least-once 与在飞覆盖

Status: proposed

## Problem

被问到「leader 与 worker 的回报有没有持久化与幂等、会不会重复投递、会不会丢消息」时逐条核过实现：会话本体由宿主 JSONL 持有并可冷恢复，worker 登记表与完成通知队列各自落盘、原子写 + 串行读改写；通知入队按 id 幂等，投递侧有进程内闸门、先摘后投、投前核对落盘队列；卡片写入走 `expectedRevision` 乐观并发。缺口不在这一层，而在在飞记录的粒度与「结算 → 落盘」的耦合。

## Proposal

- **在飞记录按会话排队，不覆盖**：`inflight` 从 `Map<sessionId, record>` 改成 `Map<sessionId, record[]>`——`message()` 追加、`settleTurn()` 取队首、空则删键。依据是「一条 `followup` 对一个 `turn/end`」：`inbox.claim` 在每个 step 开始时取走整个 `next-step` 队列，`next-turn` 只在 turn 边界取一条。
- **配套改动漏一条队列就会错位**：`inflightCount()` 改为求和；`reassignParent` 要展平到队列内每条记录，否则父会话不改、回报永久滞留；`describeRoster` 的「在跑」判定仍是「队列非空」。
- **`turnText.delete` 提到冻结 `summary` 之后、`emitNotification` 之前**：现在 delete 在 emit 之后，落盘失败时残留文本会被下一轮写进同一个 key；串不串轮由清理时机决定，与 key 粒度无关，保持单键即可。
- **放弃「在飞就拒绝投递」**：它保不住「worker 忙时 leader 追问」这个正常用法，只是把丢失换成让 leader 重试，而重试本身会重复投递。
- **结算与通知落盘解耦，重试不占后续轮次**：先从队列摘下队首、连同冻结的 `summary` / `outcome` 放进「待落盘」槽，再 `emitNotification`；失败时只重试落盘（`enqueue` 按 id 幂等），重试挂在既有的空闲轮询与补投之前，**不再借用后续 `turn/end`**——否则队首 A 落盘失败时，下一轮本属于 B 却被 A 消费，队列越长错位越多。
- **归档与销毁要清在飞记录，中断不清**：只清「这个会话已经不会再有 `turn/end`」的两种情形；停止按钮带 `keepInbox: true`、后续 `followup` 仍会被消费，清队列会把本该送达的回报改写成「被中断」。另留超时兜底（丢弃超过阈值的记录并记一行日志），兜底不代替前两条。
- **回报接受 at-least-once，重复要可识别**：`followup` 与 `markDelivered` 之间的窗口无法在应用层消除——先标记则崩溃丢通知、先投则崩溃重复一次；选择不丢，把「同一回报可能到达两次」写进限制文档。稳定 id 放进消息 `source`，让重复在会话日志与客户端里是同一个 id；不假设宿主按 message id 去重（inbox 拒收同 id 并存，那个方向走不通）。放弃「先写投递中状态再投」：只把窗口从「投→标记」挪到「标记→投」，还多一条中间态要清理。
- **任务投递不加幂等键，改为把回执语义说清**：`message_worker` 不做去重——插件分不清「模型重试」与「leader 真的要再投一次」，加一个模型必须正确填写的 messageId，填错就是静默重复。改为在工具描述与回执文案里说明「消息并入当前或下一轮，不保证只投一次」。与上一条不矛盾：回报由插件自己产生、id 可控；派工的 id 由模型生成、不可控。
- **并发补投的窄窗口一并收口**：`flushWaiting` 在循环前读一次 `pending` 快照，补投若在快照之后完成投递并标记，就会按过期快照再投一次；改为每条投递前重新核对。这只多投一次、不会丢，改它是为了让重复次数可预期。

## Alternatives considered

- **在飞就拒绝投递**：保不住「worker 忙时 leader 追问」这个正常用法，只是把丢失换成让 leader 重试，而重试本身会重复投递。
- **先写「投递中」状态再投**：只把窗口从「投→标记」挪到「标记→投」，还多一条中间态要清理。
- **依赖宿主按 message id 去重**：`inbox` 拒收同 id 并存，这个方向走不通；只能把 at-least-once 与稳定 id 写进限制。
- **给任务投递加 messageId 幂等键**：插件分不清「模型重试」与「leader 真的要再投一次」，填错就是静默重复；改为在回执里说清「不保证只投一次」。

## Acceptance criteria

现状证据（复用 `tests/dispatch.test.js` 夹具的探针，非真机）：在飞覆盖后第二条回报既不送达也不留队；`markDelivered` 失败一次再补投会多投一条；在飞两条且首次落盘失败时 leader 少一条回报；归档或销毁后 `describeRoster` 仍判该 worker 在跑。

落地必须有、且每条都做「撤销修复 → 用例变红 → 还原 → 全绿」的回归用例：在飞续投两轮各结算一条（`delivered` 累计 2）；队列内摘要不串轮；落盘失败重试不占后续轮次（队首失败 + 其后两轮，三条通知都在）；`reassignParent` 迁移队列且都投给新父会话；归档 / 销毁清队列后不再判「在跑」，反向用例是中断（`keepInbox`）后队列不清、后续回报照常送达；补投对已投出的通知不重复投、leader 只被唤醒一次。现有「一轮只结算一次回报」「通知落盘失败时保留在飞记录」两条断言不能改弱——它们钉的是同一批不变量。

## Risks

- **在飞队列仍是内存态**：进程崩溃窗口不变，重启后那一轮不结算，leader 只能自己回看 worker 会话；落盘在飞记录不在本提案范围。
- **续行上限更容易撞**：队列化后一次投多条会积累多条回报，撞上限的通知停在盘上等人工开口，界面无提示。
- **队列化的前提是「一条 followup 一个 turn」**：宿主若改成一次 turn 消费多条 `next-turn`，队列与轮次会错位，升级时按 `inbox.claim` 核对。
- **「待落盘」槽是新的一处内存态**：摘下队首后进程被杀，那条通知既不回队列也没落盘；要彻底消掉得把「已摘」也落盘。
- **清理时机不能只靠事件**：归档与销毁之后宿主是否一定补一个 `turn/end` 没有契约可依，所以清理挂在会话状态与销毁路径上再加超时兜底。
- **只影响 leader 投递的轮次**：人下钻直聊的轮次不进在飞表，行为不变。
