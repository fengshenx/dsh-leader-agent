# 项目自带一个工作区：会话归属数据层，隐藏留在渲染层

2026-11-02。

## 背景

项目会话必须能归属一个工作区，否则在官方左栏落进「未分组」；而本仓渲染层又把项目会话行藏了，那个分组只剩一个空组头。

同一个分支上先试过「项目与工作区彻底分离」（`af57681`）：协调者只带 `cwd` 建、不归属任何工作区。官方 UI 确实能打开它（`ui-workspace/src/client/navigation.ts:523-553`），但想连「未分组」组头一起藏，就得复刻宿主的可见性规则（`ui-workspace/src/client/tree.ts:229-248`）——等于把会话生命周期搬进插件，和宿主状态迟早漂移。本轮推翻那条路线，改走归属路线。

## 决策

### 建项目 = 建工作区，只认自己建的那个

`ensureWorkspace` 按 canonical 目录查，没有就 `create`；只有自建的那个记进项目记录 `workspaceId`。复用的用户工作区不记、不藏、删项目时不动。

「自建」要同时满足两条：返回的 id 不在 `create` 之前的 `list()` 快照里，且 `createdAt` 不早于这次调用。只看 id 不够——宿主 `create` 幂等（`packages/workspace/workspace/src/index.ts:510-513`），用户正好在 list 与 create 之间从管理面板加了同目录工作区时，那个 id 同样不在快照里。解析不出 `createdAt` 时按「不是我们的」处理：宁可多留一行可见的工作区，也不把用户的工作区整组藏掉、再随项目一起删掉。

### 协调者会话直接按 workspaceId 建

`createCoordinatorSessionWithCtx` 走 `sessionController.create({ workspaceId })`，cwd 由工作区 path 给出，仍是项目目录——「会话在 `~/.dsh/sessions/<cwd>/` 下」这条不变。

### worker 也归属，挂在投递之后

`agents.create` 不接受 `workspaceId`，所以建完由 `attachToWorkspace` 挂进去。fire-and-forget：归属只影响分组，挂失败只记日志，漂移可由下次点项目行自愈。日志带 `workspaceId`，否则漂移排查看不出属于哪个项目。

挂载放在 `followup` 成功之后：投递失败会销毁会话，早挂的话挂载异步落地时会话已经没了，工作区里留下一条死会话。

### 隐藏仍在渲染层

项目工作区整组藏掉（行 + 组内行 + 展开按钮），协调者/worker 会话行也藏。理由见 `docs/capability-gaps.md` 第 32、33 条：会话没有「侧栏不显示」字段，`origin` 只允许 `subagent`，归档会把会话拦在 `agent/pre-step` 之外。

### 用户删掉工作区之后按需重建

`WorkspaceRegistry.delete` 只删记录，会话与文件都不动，于是项目会话变松散、落回「未分组」。点项目行时 `attachCoordinator` 重建（`create` 幂等）并把三类会话挂回去：协调者、退役协调者、该项目的 worker。名单来自 `sessionsByProject()`——判据是目录 + worker 登记表 + 退役 id。**用户在项目目录里手动开的会话不碰**：把它们塞进一个被隐藏的工作区，等于让它们从界面上消失。

重建在左栏看不见（工作区行被藏着），所以客户端弹一条顶部提示（复用 `toast.js`，文案带归位数量）。

### 失败路径不留孤儿工作区

重建出来的工作区要写回项目记录；写入时项目可能已被另一个窗口删掉（`store.update` 抛「项目不存在」）。这时撤掉刚建的工作区：项目没了，`collectHiddenWorkspaceIds` 不再认它，它会在左栏露出一行用户没加过的目录，而插件的删除入口已随项目一起消失。回滚失败只记日志，原始错误照旧抛给调用方。

同类失败路径一并补偿：建项目时建会话失败或记录落盘失败、换协调者时归属写入失败。回滚只针对本次自建的工作区，复用的用户工作区不碰。`store.insert` 是临时文件 + `rename`，写入失败时磁盘上没有半条记录，因此「删了工作区但记录已写」不会发生；反过来，`insert` 成功之后的索引写入不会抛错，也不存在「记录已写但工作区被删」——回滚只挂在建会话与写记录这两个失败点上。

### 打开与换协调者前先确认目录还在

宿主注册工作区不校验目录；等挂会话时才 realpath 会话 cwd，抛一句英文技术错（`cannot attach session …: its cwd '…' does not resolve`）。`attachCoordinator` 与 `replaceCoordinator` 都先过 `assertUsableDirectory`：目录不在就回「项目目录不存在或不可访问：…。把这个目录恢复回来，或删掉该项目后重新添加。」，顺带避免凭空注册一个指向已删目录的工作区。打开路径返回 `reason`（客户端展示），换协调者抛错（工具调用失败）。

## 边界

- 「未分组」组头在工作区被删、又还没点过项目行的窗口期会露出来（组里没有可见行，因为我们把插件会话藏了）。不复刻宿主可见性规则是刻意的。
- 工作区仍在宿主数据里：欢迎页的工作区选择器、工作区管理面板列得出来，用户能从那里删掉它（然后走上面的重建路径）。
- 官方分组行上的会话计数包含被隐藏的行；被隐藏的行仍在 DOM 里，官方搜索仍能命中。
- 目录已有用户自己的工作区时会被复用：不记 `workspaceId`、不藏，于是项目会话挂在用户的工作区里、行被藏，那个分组的计数比可见行多。
- 「自建」判据的 `createdAt` 下限依赖本机时钟：窗口是 `requestedAt` 到宿主 `createCanonical` 落盘之间（含注册表写队列的等待，可能不止 1ms），用户恰好在这个窗口里从面板加同目录工作区仍可能被认成自建；时钟回拨只会让插件少认自己的工作区（表现为多一行可见的工作区）。两个方向都不动用户数据。
- worker 挂载失败不重试：只影响它是否落在「未分组」，下次点项目行会带回。

## 验证

- `npm run check`（含 Agent Note 格式门禁，36 篇）：595 tests / 595 pass / 0 fail。
- 回滚四处各有用例：打开项目时项目被并发删掉、建项目时建会话失败、建项目时记录落盘失败、换协调者时归属写入失败；每条断言 `registry.list()` 里没有新注册的工作区。
- 双向验证（撤掉修复 → 对应用例变红 → 还原 → 全绿）：
  1. 去掉 `createdAt` 下限 → 「list 与 create 之间用户加了同目录工作区」红；
  2. 去掉 `recordWorkspaceOwnership` 的回滚 → 「打开项目时项目被并发删掉」与「换协调者时归属写入失败」两条红；
  3. 去掉建会话失败路径的回滚 → 「建会话失败时不留刚注册的工作区」红；
  4. 去掉落盘失败路径的回滚 → 「项目落盘失败时不留刚注册的工作区」红；
  5. 把挂载移回投递之前 → 「投递失败销毁会话时不把它挂进工作区」红；
  6. 日志去掉 `workspaceId` → 「挂载失败不拖累派工」红；
  7. 去掉 `replaceCoordinator` 的 `assertUsableDirectory` → 「换新协调者前先确认项目目录还在」红；
  8. 去掉 worker 身份过滤 → 「不碰用户在同一目录里手动开的会话」红。
- 对抗探针（并发重建）：两个 `attachCoordinator` 同时跑（假 registry 照宿主幂等语义）→ 只建 1 个工作区，`attachSession` 去重，两次调用都报 `attached/recreated/reconnected: 1`，记录指向同一个 id。
- 真机（隔离实例，零真实 API 调用）：建项目后左栏只余 `Default workspace`，项目工作区行 `display:none`；手工把该工作区从 `workspace.json` 删掉并重启后点项目行，提示条读出「项目「own」的工作区已重建，1 个会话已归位。」，重建的工作区行与会话行都是 `display:none`，无 console error / pageerror。
