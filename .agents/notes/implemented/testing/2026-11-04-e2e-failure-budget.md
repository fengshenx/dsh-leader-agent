# e2e 失败预算与页面读数

## 背景

排查一条场景时单跑要 66 秒才失败，而正常场景只有几秒：元素等待写成 60 秒，元素不出现就干等满一分钟；报错又只有一句「等待超时」，分不清不在 DOM、不可见还是零尺寸。

## 决策

- **元素等待统一走 `waitForLocator()`**：默认 15 秒，首次启动后的元素（输入框、项目行、工作区行）20 秒；`waitFor()`（落盘、轮询条件）保持 15 秒；`E2E_BUDGET_SCALE` 整体放大二者，非法值告警一次后按 1——静默忽略会让人以为已经放宽。
- **预算按正常耗时给**：单场景 3–8 秒、元素 1–2 秒到位，20 秒已是十倍余量；写 60 / 90 秒不会更稳，只把失败拖成一分钟。
- **失败时附目标与页面读数**：目标元素的 `count` / `visible` / `boundingBox` / `checkVisibility` / `display` / `visibility` / `opacity` / 宽高，加上页面行 key、输入框是否可编辑、插件容器与项目行计数，用来区分「数据没到」与「渲染错了」；读数不参与断言。
- **读数自身有预算**：`page.evaluate` 没有 timeout，页面主线程卡死会一直挂着；每段读数限 2 秒，超时退化成 `{ unavailable }` / `{ error }`，两段并行。
- **页面已关闭与元素没出现分开报**：只有 `TimeoutError` 写「等待超时（预算）」，其余写「等待失败：<首行>」——前者查选择器，后者查清理与崩溃。
- **文档补纪律**：缺 `lib/client.js` 的症状是全线超时（车道前提），预算与失败读数写进断言纪律与失败诊断。

## 边界

- 不引入重试：重试只会把竞态藏起来。
- 不把预算压到秒级：慢机冷启动需要余量；覆盖入口只放大默认值，默认值不动。
- 读数上限不随 `E2E_BUDGET_SCALE` 放大：它防的是页面卡死，放大只会把卡死重新变成慢失败。
- 页面读数不是快照或 golden，不承诺结构稳定。
- 不改 `t.after` 的清理顺序与 `problems` 断言；`instance.stop()` 的信号链见 [e2e 清理阶段的有界等待](2026-11-04-e2e-shutdown-bounded.md)。

## 验证

`tests/e2e-harness.test.js` 钉住 `waitForLocator`、读数预算与倍率；双向读数：撤掉读数里的可见性/尺寸字段后，`display:none`、零尺寸、`visibility:hidden` 三种形态退化成同一个 `{ count: 1 }`；页面卡死时去掉读数预算，同一读数从 2 秒拖成 10 秒。
