# worker 回报的投递边界与时机

## 背景

用户要求 worker 回报**走下一个 turn**，并且**不要显示在宿主输入框上方的「消息队列」面板**里。宿主 agent 的投递都经 inbox 的两个边界（`next-turn` / `next-step`），那个面板读的正是未被消费的 `next-turn` 队列，第三方没有插过滤位的位置。

## 决策

- **完成通知走 `next-turn` 边界（`followup`），且只在父会话空闲时投**：协调者正忙时投进 `next-turn`，它会以「一条待发消息」的形态挂在用户输入队列上。改为忙时不投：通知留在落盘队列，进程内的等待表记着它，每 500ms 轮询父会话状态，`agent.status === 'idle'` 才投。投递即被消费，面板看不到；唤醒时机与排进 `next-turn` 几乎一样。
- **投递前三道闸门**：轮询回调加 in-flight 闸门，`flushWaiting` 先摘后投，`deliverNow` 按通知 id 幂等；投递前还要核对通知仍在落盘队列里——补投通道可能已经投过同一条。
- **投递结果三态 `delivered` / `retryable` / `exhausted`**：撞续行上限属不可重试，不回填等待表、不再每轮重试、只记一次原因（带积压条数）；条目仍留在等待表并打上标记，轮询跳过它，用户开口时计数复位、标记清掉后才重新投得出去——直接丢弃会连「人工介入后可恢复」这个性质一起切掉。
- **续行上限只在真正投递时计数**：等待期间不消耗额度。
- **等待表按父会话分组、存 `{ notification, agent }`**：必须记住 agent 活对象，空闲检测没有第二个入口能拿到它。
- **定时器回调必须 `.catch()`**：里面读盘写盘，未处理拒绝在宿主那边是致命退出。定时器 `unref()`，`ctx.on('dispose')` 停掉，并用 `closed` 标志让 `deliver` / `ensureIdleTimer` 早退。
- **卡片排序要能注入时钟**：按更新时间戳排序时，两次写入落在同一毫秒会退回插入序；存储接受注入时钟，测试用可控时钟钉住顺序。
- **旧记录要做读取退回**：改造前落盘的通知没有 `summary`，取摘要要兜住非字符串、给默认值、退回正文首行，否则那条通知永远投不出去。
- **Trajectory 里 worker 回报归类为 `CONTEXT` 行**（宿主按 `source.kind` 分类），与投递边界无关。

## 边界

- **等待表没有上限**：父会话长期忙时按 worker 数累积，每 500ms 全量 `listPending`；实测成本可忽略，但没有淘汰与告警。
- **积压在界面上不可见**：忙完后只投出护栏允许的条数，剩下的要等用户开口才放行，用户和协调者都看不到还有多少条在等——唯一端倪是撞上限时写下的原因。
- **空闲判定与用户输入之间没有互斥**：轮询恰好落在「用户回车 → driver 起跑」之前时，回报会与用户那条短暂排在同一个队列条里；要彻底收口得在投递前查一次 `next-turn` 是否为空。
- **投递与落盘顺序**：消息先到父会话，「已投递」标记随后才清；界面无感，但断言要等两件事都成立。
- **`followup` 抛错会被兜住**，通知留在落盘队列等补投；catch 只包这一次调用，摘要构造与标记清理在它外面。

## 验证

`tests/dispatch.test.js` 与 `tests/notification-store.test.js` 钉住投递时机、幂等与三态。双向读数：撤掉空闲闸门，用例读到消息队列里多出 worker 回报而变红；去掉 `exhausted` 标记，用例读到每 500ms 重复重试而变红。
