# 换协调者的四类边界：并发写入、client 身份、退役后的工具面与 worker 接管

## 背景

换协调者会把旧会话留在项目下、与 worker 同列（见 [退役协调者会话](../feature/2026-10-30-retired-coordinator-sessions.md)）。修的过程中露出两层问题：一是「换人」不等于「新会话接过项目」——`COORDINATOR.md` 承诺新会话立刻接手，而原班 worker 的派工归属仍挂在退役会话上；二是补投路径在「一次投出 ≥1 条」时整表删等待表，把同一轮刚进去的条目一起丢掉。四类边界（列表、身份、工具面、派工归属）各有各的口径，而工具面只在 `agent/created` 裁一次、换人不重建会话，所以凡「退役之后不该再有」的能力都只能在调用时判。

## 决策

- **并发换协调者：退役追加必须是读-改-写**。`update(id, fn)` 接受函数形态，参数是磁盘上的当前记录，读-改-写落在存储的串行链里；退役的是**落盘记录里的**当前协调者，不是进函数时的快照。
- **白名单在函数求值之后套用**（函数对象自带 `name`），函数必须同步返回普通对象（返回 `undefined` / 字符串 / Promise 都静默不生效）。
- **并发不合并**：两次点击仍建两个会话，落选的那个进退役列表（项目下可打开的历史），不是孤儿。
- **索引对齐按重读记录，不按 `update` 的返回值**：返回值只是「这一次写下的状态」，按它对齐等于把正确性押在微任务顺序上，晚到的同步会把已被退役的会话重新写成协调者。写完重读一次记录按最新值对齐，晚到者只会朝最新值收敛。
- **对齐放在失败路径之外**：写已经落盘、新会话就是记录里的协调者，重读失败不该把它连带撤销。
- **client 侧：项目会话表不是 worker 表**。`summarizeProject` 带出退役集合，相关命名从 `fetchProjectWorkers` / `isProjectWorker` 改为 `fetchProjectSessions` / `isProjectSession`，身份再分一次。
- **退役判定放在 client 的纯函数里**：`isRetiredCoordinatorSession` 在视图状态、可见性与访问权三处显式排除；退役会话的出口是 `not-viewable`（与同目录普通会话同一句提示），不给「去换新协调者」的引导——它自己就是被换下来的那个。
- **host 侧不把退役 id 从表里剔掉**：同一张表还给项目树用，退役会话必须留在项目树下。
- **退役后的工具面校验只能放在调用时**：工具面在 `agent/created` 一次性裁、换人不重建旧会话，退役会话手里仍留着协调者工具直到进程重启；冷恢复会走「非协调者」分支，缺口只在同进程的存量会话。
- **`dispatch` 与 `message` 共用 `assertCoordinator`**（先等索引再判身份，不吃「索引未就绪就放行」的宽松），在投递前判定而不是拦住后补——退役会话给原班 worker 下指令，是把「谁是协调者」判错了，不是投递失败。
- **`list_cards` 的跨项目读取一并收口**：`scope: 'all'` 与单卡 `cardId` 都过同一身份闸，判据取退役集合而不是「必须是协调者」（将来放宽工具面也不会误伤 worker）。
- **两条路径都拒且返回报错而不是空列表**：空列表会把「你没权限」伪装成「全库没有卡」。默认 `scope: 'project'` 照旧放行，单卡不做「属于本项目就放行」的细分，需要全文时交给当前协调者。
- **换人之后原班 worker 归新协调者：接管而不是重新派工**。接管在 `replaceCoordinator` 成功后触发（晚绑定装配：接管依赖派工器，派工器依赖项目服务）。登记表改 `parentSessionId`，旧父会话追加进 `reassignedFrom`——「谁派的工」是历史事实；通知队列只改未投递的；等待表按到达顺序拼到接手会话已有条目之前，条目里的通知跟着改父会话 id 并丢掉旧 agent，续行计数取两者较大值，在飞记录改父会话。
- **改投过来的通知推一次投递**：新会话的 `agent/created` 早于这次迁移，那一刻队列里还没有它的事，不推就一直躺在盘上。
- **接手方与退役集取当前落盘记录**，不取调用那次写下的值：两次并发换人时，先完成的那次接管可能到记录已改成第三个人之后才执行；按当前记录算每次都朝最新值收敛，顺带补上早先漏迁的孤儿。
- **补投不清等待表**：`flushWaiting` 本来就按落盘队列逐条核对，已投出的会自己掉出去；整表删除会丢掉同一轮里刚进表的条目，web 里会话常驻时表现为「一直没送到」。
- **等待表条目必须改 `parentSessionId`**：否则 `deliverOnce` 仍按旧 id 取续行计数（护栏被换人绕过），销毁判定也查旧 id。
- **登记表改绑命中 0 条时不写盘**：接管对每个退役 id 调一次，退役列表只增不删，每次都空读改写太浪费。

## 边界

- **接管失败不回滚**：那次项目记录已经改绑，用户会看到「换协调者失败」而实际协调者已换；回滚要重建一条已经停掉的新会话，代价更大。再点一次换协调者会把没迁完的补齐（接管幂等）。
- **新会话不可达时不回落到退役会话**：回报留在盘上等它下次可达；宁可晚到，也不投进一条已经没有工具面的会话。
- **队列条目不留 `reassignedFrom`**：它不是历史记录，改投后只有一个归属；要追溯看登记表。`resumeCounts` 取较大值，人工在新会话开口会复位。
- **`list_cards` 解析不到项目时放行**：会话连项目归属都没有时判不出退役身份，读类工具按放行处理。
- **只解决同一项目内换人**：跨协调者、跨项目的 worker 仍被父会话校验拦住。
