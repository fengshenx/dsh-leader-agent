# Agent Note: 文档预算的单一余量公式与 10% 专项门禁

Status: implemented

## Problem

同一份文档的余量曾出现两套算法：门禁用 `天花板 / 当前值 − 1`，审查另用 `(天花板 − 当前值) / 天花板`。16420/18171 在正式公式下是 10.66%，另一套算成 9.64%，同一组数字得出相反结论，造成返工。更根本的是 `AGENTS.md` 要求 `AGENTS.md` 与 `docs/capability-gaps.md` 留 10%，脚本里却只有 5% 下界，10% 一直靠人工手算；手算又可能用错公式。`headroomPercent` 还在 5% 以上向下取整，5.46% 会被印成 5.45%，正文与门禁读数对不齐。

## Decision

- **只保留一套公式**：余量固定为 `ceiling / units − 1`。判定、展示、PR 读数都回到这个值，不引入第二种分母。
- **专项下限进入清单**：`scripts/doc-budgets.json` 的条目可以是纯数字天花板，也可以写成 `{ ceiling, minHeadroom }`；目前只有 `AGENTS.md` 与 `docs/capability-gaps.md` 登记 `minHeadroom: 10`，机制可扩展到其它文档。
- **专项失败有独立状态**：低于登记下限报 `tight-special`，输出 `TIGHT*`，错误文案明确「该文档要求留 X%」；未登记专项下限的文档仍按 5% 判 `tight`，12% 上界与 `small` 豁免不变。
- **展示与判定同源**：低于 5% 时截断到两位小数，避免 4.999% 印成 5.00%；5% 以上正常四舍五入，5.46% 不再变成 5.45%。
- **不改任何天花板**：本任务只改清单结构、脚本与规则文本，现有 21 篇文档的数值不动。

## Alternatives considered

- **继续只在 `AGENTS.md` 写 10%、靠人记**：已经证明会与 5% 混用，且同一数字出现两套结论；不编码就无法在 CI 拦住。
- **把 10% 写成全局下界**：会把所有文档都抬到 10%，与现有 5% 政策和 21 篇读数冲突，改变范围远大于本任务。
- **审查侧改用自己的公式**：仓库已有唯一实现，再维护第二套公式只会增加漂移；统一到 `doc-budget.mjs` 才能让门禁、正文和审查读同一个数。
- **把专项下限硬编码在脚本里**：新增文档时又要改代码；放进清单让“哪个文档、多少下限”成为配置事实。

## Consequences

- 清单出现两种条目形状：纯数字是普通文档，对象必须带 `ceiling`，可选 `minHeadroom`；读取方要按形状归一化。
- 只有两份高频文档享受专项下限；其它文档仍是 5–12%，不会因这次改动被动加严。
- 取舍是清单略复杂、测试多一组专项分支；换来的是 10% 规则可机械验证，审查不再手算，展示值不再与判定打架。
- 收益：余量只有一个定义、一个数字，专项规则不再依赖记忆。

## Testing

`tests/doc-budget.test.js` 覆盖 10% 专项红/绿、10.0% 边界、`small` 豁免不被专项误伤、5%/12% 边界、5.46% 取整，以及真实清单只有 `AGENTS.md` 与 `docs/capability-gaps.md` 登记专项下限。双向验证用 9.5% 夹具跑真实门禁：变红并指出要求 10%，恢复到 10% 后转绿。
