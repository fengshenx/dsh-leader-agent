# 协调者手册把 routing 边界写死

## 背景

手册原来写「功能代码交 worker 实现」，把实现面收在一个「代码」字眼上——测试、文档、配置仍留在协调者手里；紧接着一句「局部问题直接处理」又给了自己动手的合法入口。后果是一次 PR 由协调者代写，事后要 worker 接管重做，卡才重新有真实执行者与验证记录。

## 决策

- **协调者只做 routing，不留例外**：目标、拆分、派工、验收、合并与收尾；不亲自落地——代码、测试、文档、配置的改动一律派 worker。协调者亲手改的那一刻，卡就不再对应真实执行者，验收退化成自己验自己。
- **「非得自己动手」按拆卡处理**：觉得必须亲手改，说明范围在派工后变了——按新范围记卡、补简报再派。措辞必须无条件，「真需要时」这类限定语一出现，例外就成了可援引的口子。
- **只读判断不算落地**：读一段代码、答一个疑问、比对 diff 与输出可以直接给结论；判据是有没有产出改动，不是事情大小——「改一行配置」正是漏进来的第一道口子。
- **产出挂卡要带并发校验**：`update_card` 的 `links` 是整体替换，只写「先读卡带上已有条目」在跨会话并发下仍会丢条目；要求同时带 `expectedRevision`，版本不符即拒写，冲突就重读再写。
- **别处已有的规则只留指针**：手册改成一行断言加指针，只保留它独有的参数细节（`cardId`）。指针必须指得到依据，指不到就把那半条留在原地——`SendMessage` 不在那些文档里，只能在手册直写。

## 边界

- 一行配置的紧急修复也要先记卡、补简报再派，协调者多一轮往返。
- 判据落在「有没有产出改动」上，仍要人判断；措辞里一旦出现限定语，例外就会重新长出来。

## 验证

纯提示词改动，无用例；口径复查是通篇扫「直接处理 / 例外 / 亲手 / 自己」，除只读判断外没有留下协调者可亲自落地的表述。
