# 派工结算的挂载顺序、索引就绪与看板容错

## 背景

实现中发现派工链路上有三处把失败记成成功（登记失败丢通知、续聊竞态抛错、续聊轮失败报完成），协调者判定 `fail-open` 却没有执行期兜底，看板一次 RPC 抖动就永久停在错误页。

## 决策

> **结算机制已换**：2026-10-29 起由 `session/event` 的 `turn/end` 结算，`activation.result`、`subagent/end` 与 `judgeTerminal` 均已删除。本笔记前三段（挂载顺序、续聊竞态、`stopReason`）保留为当时的缺陷记录，现行实现见 [worker 的完成回报由机制侧从会话事件结算](../architecture/2026-10-29-worker-report-by-session-events.md)。

当时那三处缺陷是：结算回调挂在登记之后（登记失败就白跑）、`await` 之后回查记录（可能已被结算删掉）、续聊轮硬编码 `ok: true`。

**派工不能建立在索引 fail-open 上。** `isCoordinatorSession()` 在索引未就绪时一律放行，那是为了让协调者首轮看得到工具；但注册表读不出来时任何会话都会被当成协调者。派工是唯一会真的拉起会话的操作，执行前等一次索引重建结果，读不出来就拒绝，并要求调用方确实是协调者。读类工具保持同步判定——多给一个读工具的危害是「看不到卡片列表」，不是拉起会话。

**索引重建失败退避重试三次。** 只试一次会让索引永久停在未加载、派工全废；退避重试仍失败则由派工路径明确报错，让用户知道要重启。重试定时器随插件的 `dispose` 一起清掉。

**`coordinatorIndex` 是必需参数，装配时断言。** 漏传即静默跳过整段派工校验；宁可装配时当场报错，也不留一个悄悄少一道闸的入口。测试用 helper 提供默认放行实现。

**看板 RPC 抖动不判死。** 成功时清错，轮询失败保留已加载的卡片；轮询本来就是自愈机制，把面板钉在错误页等于扔掉它。

**卸载时只关自己开的 tab。** 遍历 `openTabs`，只按本 kind 关闭；不关会叠一个点开即空的看板，也别碰用户别的 tab 或整栏清空。

**登记表只留 `register` / `get`，并设上限。** 未使用的查询接口按「未使用代码直接删除」删掉；记录永不删除且每条带任务正文，不设上限时文件随派工次数无界增长、每次登记整表读改写——保留最近 500 条，同毫秒登记时稳定淘汰更早那条。

**`needed` 用 id 排序串当依赖。** 卡片每次轮询换一个新数组，用 Map 当依赖会让同步效果每轮重跑，保留失败的槽位每次再 retain 一遍（`reported` 只挡住日志，调用没停）。

## 边界

- **`list_cards` 的单卡查询跨项目可读**：传 `cardId` 走全库查找，不做项目过滤；写权限必须收紧（`update_card` 会拦）。读权限放开是有意取舍，要收紧时改这一处与两个远程方法，不是散在各工具里。
- **`onError` 的覆盖面窄**：兜底地址之后保留调用不再抛错，只剩「宿主认地址、但快照永远不来」这条静默路径；保留租约没有超时事件，判不出来。
- React 侧改动（看板清错、卸载关 tab、`needed` 稳定键）进不了单测：本仓不引 React 与 jsdom，靠代码审阅。

## 验证

`tests/dispatch.test.js` 与 `tests/worker-registry.test.js`：撤销挂载顺序时报「登记失败仍照常投递完成通知」的用例变红；去掉索引就绪分支时报「索引读不出来时拒绝派工」的用例变红；还原后全绿。
