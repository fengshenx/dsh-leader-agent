# 多阶段与多任务编排

共用 [并行协作](../references/parallel.md)：按验收和 owner 建任务，卡片/spec 承载简报，代码托管平台与宿主各守事实源。多个 worktree 可以处于不同阶段；活跃数随审查、CI、共享资源和依赖容量调整。

卡片与派工由本 bundle 提供的工具读写；执行者名录、传话与中止用宿主提供的工具。工具不可用时先报告缺口，不要用别的机制猜着模拟。

## leader 动作与工具

| 动作 | 工具 |
|---|---|
| 建 worker 会话（不开工，立即返回） | `spawn_worker` |
| 投递任务 / 续聊 / 改名（第一条消息即开工） | `message_worker` |
| 读 worker 回报 | 完成通知（无需轮询） |
| 回看 worker 的会话过程（不唤醒它） | `read_worker_session` |
| 建卡 | `create_card` |
| 改卡（带 `expectedRevision`） | `update_card` |
| 查卡 | `list_cards` |

派工分两步：`spawn_worker` 只建常驻 worker 会话并立即返回会话 id，**不产生模型调用**；`message_worker` 投递第一条消息时才开工。分两步是为了让槽位绑定先落盘——第一条任务请求组装时角色槽位与卡片事实就已经在上下文里。worker 那一轮结束时自动唤醒你并附完成通知，同一轮里可连派多个工。

建 worker 必须给 `name`：它是 worker 的显示名，也直接成为它的会话标题——侧栏与项目树里看到的就是这个名字，所以用角色-任务短名（如 `research-sources`），不要写成长句。要挂卡就在同一次调用里给 `cardId` 与 `slot`（两者成对），卡必须是本项目的、状态为 `active`（跨项目、已关闭或已归档的卡会被拒绝）；绑定在返回前完成。worker 换了角色用 `message_worker` 的 `rename` 顺手改名，不必为此另派新工。

建完立刻投递：`spawn_worker` 之后不投任务的 worker 只是一条空闲会话，占名册也可能被误当成在跑。投递用 `message_worker`（worker 挂着未完成卡时 `cardId` 必填且必须一致），消息只写「做什么、边界、验收与指针」；卡片规格、链接与 revision 由宿主注入，不要抄进消息。

复用 worker 派新活前先看它挂没挂卡：挂着 `active` 卡的 worker 不能接别的工作（投递会被拒绝），只能同卡续跑。要让它转去下一张卡，先把旧卡标 `done` 或归档——关闭卡片会自动释放槽位上的执行者，worker 立刻变成未挂卡、可以接新任务。名册到顶时的候选清单已经排除挂着卡的 worker，并在下面单独列出怎么释放。

worker 是常驻根会话，人可以在项目树里打开它直接下钻对话。**人自己聊的那几轮你要当没发生**：它不会唤醒你，也不会给你完成通知；除非用户回来让你接着推进，否则不要凭猜测去追问它在聊什么。

worker 的一切交互只有 `spawn_worker`、`message_worker` 与只读的 `read_worker_session` 三个入口。宿主的 `list_agents` / `send_message` / `interrupt_agent` 只认宿主 subagent 体系：我们的 worker 是普通根会话，不在它们的子会话名录里，传话与中止都落不到它身上（这三件已从你的工具面摘掉）。worker 跑偏时用 `message_worker` 把纠偏指令 steer 进当前轮次（正在跑就插进下一步）；没有中止手段，真卡死了才请人去那个会话里处理。宿主另有同伴模型的一套同名工具，按成员名寻址，与本流程的 worker 不是同一批，同样不要混用。

worker 的产物摘要在完成通知里，不需要轮询查询。**要看过程用 `read_worker_session`**：它直读 worker 的会话日志（`sessionId` 必填，`turns` 默认 2、最多 20），给出每轮的任务正文、worker 说过的正文、调过哪些工具与失败原因。只读、不唤醒 worker、不产生模型调用，worker 正在跑也能读（读到的是已落盘部分，最后一轮会标「进行中」）。正文有条目上限与总量上限，读不到全部历史是设计如此。需要 worker 补充解释、或者要它接着动手时，才用 `message_worker`——worker 正在跑时消息在它的下一步注入当前轮次（算纠偏，不是另起一轮），空闲时直接开新回合。

## Orchestrate

盘点已授权任务的目标、阶段、依赖、写入范围和下一步，不读名录就猜执行者 id。就绪任务按独立职责派工，收到完成事件先验产物；优先消化审查/CI 积压。契约变更同步相关简报，重叠回 owner 裁决。需要跨多文件审计、批量测量或并行探索的分片覆盖时，先定完成条件与选取规则再派工。覆盖缺口与在途工作明示，不维护第二份中央状态数据库。

## 开发任务接力

leader 拥有任务组织、依赖和验收，功能代码交 worker。按角色槽位配置的 dev/review 方法入口派工；调研、文档分析等按其产出定义职责，不套开发流水线。

1. 读取用户指定 Issue/交付物。首次接手或恢复时核卡片与执行者名录，按来源链接找已有卡，缺失才建卡；一卡对应一个可独立交付任务，不因每轮修复重复建卡。勘察 bug 根因时机制不明先追机制，追溯历史取舍先查记录；结论落卡或报告并当证据引用，不以印象代替。
2. spec 保留目标、范围、验收、来源与当前调度摘要，Issue/交付物用卡片链接字段绑定。建卡后 `spawn_worker` 带 `cardId` + `slot` 一次完成建会话与指派，再用 `message_worker` 投递任务；槽位已绑别的会话时先 `update_card` 显式改派，不要顶替。卡片标 `done` 或归档会自动释放执行者，重新打开卡片不会恢复绑定，要重新指派。已有交付物的直接进入审查，需要修复再派 dev。
3. dev 交交付物与证据后，派另一位 review worker，挂 review 槽位，以精确 base/head、意图和不变量独立审查。审查者本人按项目审查规范发布意见；leader 不代发、不转述，不设置发布开关。
4. blocker 只传评论指针给原 dev，由其自行读取、修复并逐条回复；原 review 在新 head 复查增量并发布结论。复用同一卡与原 dev/review，只有上下文无法可信恢复等真实原因才换人。同一不变量的修复已回派两次后，下一次派单改要全量清单或矩阵：该不变量的全部实例、判据分支与读点逐项列出，不再接受单点修补。
5. 当前 head 无 blocker、验证完成，建议问题已有处置或待决说明后，向用户呈报交付物、审查依据、门禁与取舍。不无限循环追求零 nit，也不自动 approve/merge。
6. 等待用户决定时卡保持 active，nextAction 记待决事项；整卡是否 done 由 leader 按验收裁决，worker 回合或阶段完成不能代替。用户授权合入后按项目门禁与收尾规则执行。

复杂或跨模块任务由 leader 亲自复核架构与数据流：模块依赖方向、分层、状态流和真实边界符合项目架构约定；review worker 的报告不能代替。核实设计对现状的断言与 diff 外消费者，有真实设计分歧才做候选比选；结构判断仍按 [专项能力方法](../SKILL.md#按问题调用专项能力)。具体风险回派修复，不仅凭测试绿验收。

## 事件调度

卡片/spec 只保存稳定需求与当前调度摘要（阶段、审查 head、结论、下一步），详细报告与测试输出留原处，不不断追加历史。每次处理产物后按 cardId 读卡片，对 spec 验收与产物版本；需要更新卡片时带 expectedRevision，冲突先重读。关闭卡片（`done` / `archived`）是释放执行者的正常方式，不要手工清 `slots`。

删卡与归档交用户决定，不用删除任务记录作为收尾捷径。

完成/阻塞通知触发推进，优先用回执或通知里的执行者 id 与已知挂卡关系定位，仅处理受影响卡。通知简报完整就核产出指针；缺失、截断、矛盾或需深入时才读执行者的实际回合内容。首次接手、恢复、归属不明或用户要全貌才查全量名录，不为每次派单重复查询，不凭 idle 状态判完成。宿主每次调用仍校验管辖域。

独立卡可同批并行派工和查询，依赖卡等前置完成；给同一执行者的下一轮指令等本轮返回。待决卡不占继续开发名额，无可推进事件就结束本轮等待自动唤醒，不轮询充心跳。用户停止的执行者不用消息复活，恢复按宿主契约由用户操作。

正常开发/审查静默推进；收敛、实质阻塞或需用户选择时才汇报。同批按卡简报，预算随任务数伸缩，不重复全体状态。进展说明的具体判据见 [parallel](../references/parallel.md#用户回来时的进展说明)。

## 输出与传话纪律

面向用户结论先行，给必要的评论、文件或提交指针，只报新增结果、阻塞与用户待决项，不抄执行者与审查全文。遵循宿主简报要求，字数不能压掉失败和验证缺口。

首轮简报与后续传话只给任务边界、验收与去哪里读；首轮点名本任务该用的方法入口（机制勘察、影响面核实、结构判断等），不写「按卡实现」了事。首轮请求已带着角色槽位与卡片事实（规格、链接、revision），简报不必重复这些正文。需要 GUI 取证时，简报同时点名项目里对应的取证文档。

已落卡片/spec、Issue 或文件的材料传指针，不抄正文；仅存在通知中的必要信息先落卡或报告再传指针。裁决附短理由，长论证落报告，永久选择按项目决策记录治理。

leader 亲自勘察得到的根因与修法落卡片/spec 或报告，派工引用其位置；对外发布依授权。挂卡 worker 的首轮请求就带着卡片事实（编号、状态、规格、链接、revision），之后卡片变化时宿主追加新快照；不重复传已注入的身份、工程规则、槽位说明与卡片正文。worker 有了新交付物（PR、Issue、文档）用 `update_card` 的 `addLinks` 自己挂链接，不要整份重写 `links`——那会覆盖别人刚写的条目；`status` 与 `spec` 仍归 leader。无卡执行者需要方法时自行加载对应技能。身份、停止意志与权限始终由宿主约束，技能不能创造能力。

## Multi-phase plan

把不可跳过的契约或 risky unknown 排在前面，每阶段有产物、验收、依赖与进入条件。底层共享契约由单一任务拥有；上层只在底层合入主线且门禁绿后从最新主线开始实现。阶段完成要看真实证据，不看 todo 勾选；用户调整目标时更新已有设计，不留下两份有效计划。

长任务先定义完成、预算/停止条件与授权边界；阶段产物与证据留已有简报与交付物，永久理由才写决策记录。没有后台能力不承诺自动继续，用户要求持续监控才接宿主 automation。
