# 测试与验证

测试不是「跑过命令」，而是用最便宜、能证伪的手段证明可观察行为成立。先定验收与可观察量，再选层；能用纯函数、夹具或落盘断言证明的不上浏览器。项目自己的测试命令、覆盖率门槛、flake 表与人工取证范围是事实源，本 playbook 只给方法与检查点。

## 选层

- **纯函数 / 数据转换 / 状态归一 / 落盘格式**：单测。输入输出可判定，不需要运行时。
- **构建、打包、profile、门禁**：用项目自带的构建与打包检查，不另造一套断言。
- **真实 UI 行为**：项目的 e2e 车道。先读项目里的车道文档与场景写法，不自己另起一套。
- **样式、像素、动画、原生控件、跨浏览器**：人工取证；自动回归只守行为与已修 bug 的最小几何守卫，不守观感。

同一条结论有更便宜的层就不要升级；e2e 只补单测证明不了的那一段。

## 写用例

- **先失败再修**：bug 先复现正确失败，feature 先固定用户路径，重构先固定消费者行为。方法见[实现 playbook](implementation.md)。
- **断言外部可观察量**：返回值、落盘文件、DOM 属性与可见性、ARIA、wire、投影。不读内部调用栈或自述。
- **假件照真实 API 面构造**：多给一个宿主方法，会掩盖下限版本的能力缺口。
- **一次只改一个变量**：用例名写清守住的那句话；去掉不稳定的时序依赖。
- **边界与反向路径至少各有一条**：空值、越界、失败、取消、重复提交。
- e2e 场景的断言纪律、等待预算与失败读数见 [e2e-scenarios](../../e2e-scenarios/SKILL.md)。

## 双向验证

修 bug 与重大回归必须：撤掉修复（或注入缺陷）→ 对应用例变红 → 还原 → 全绿。没变红先怀疑用例，不先怀疑实现；把「撤掉什么、红了哪条、报什么读数」写进交付物。重大缺陷固化为永久回归。

## 证据与门禁

- 按项目门禁跑最小检查；交付物写清跑了什么、结果、未跑项与原因。不贴一条命令当证据，不把 worker PASS 当验收；PR 证据格式见[交付 playbook](delivery.md#开-pr)。
- 失败先读目标/页面读数、日志与请求记录，区分数据没到、渲染错了、环境坏了；不靠重试或加大等待变绿。
- 已知 flake 要登记并追根因；同一处连续两次空载失败按回归处理。
- 截图与临时数据不入库；截图只解释当时状态，不替代断言。
- 覆盖数字只作下限：新增文件默认要求全覆盖，加载不到的文件要登记理由，不靠漏测或空导入变绿。

## 审查测试

- 断言是否落在可观察行为上，而不是实现细节？
- 撤掉修复后这条用例会红吗？
- 假件是否比真实 API 面多给了能力？
- 是否有只证明「代码执行过」的绿灯？
- e2e 是否在测样式、像素或动画？是则删掉或转人工取证；只有已修 bug 的最小相对几何守卫可以留，基准必须是宿主同一元素。
- 覆盖数字是否靠加载文件凑出来，而不是覆盖行为？

## 不覆盖

原生控件、样式与像素布局、WebKit/Firefox 走人工取证并在交付物里标注；不真实调用付费模型 API；不把 e2e 塞进只跑纯函数的门禁。
