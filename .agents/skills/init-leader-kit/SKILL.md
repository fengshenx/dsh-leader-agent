# 项目初始化

把项目上下文固化到三份文件，让后续会话自动遵守，不依赖人工重复交代：

| 文件 | 解决什么 | 谁读 |
|---|---|---|
| `AGENTS.md` | 工程约定（语言、注释、测试、提交流程） | 所有会话 |
| `LEADER.md` | 这个项目的 leader 怎么指挥：职责边界、派工、验收、硬约束 | 项目的 leader 会话，每轮注入 |
| `SLOTS.md` | 执行者角色（dev / review）各自怎么做 | 被卡片绑到槽位的会话 |

## 一、先看目录现状

先读目标目录，再决定写什么：

- 有 `README.md`、`AGENTS.md`、语言清单文件（`package.json`、`pyproject.toml` 等）就读一遍；有 git 仓库就看最近提交。
- **空目录、或几乎没有可用信息时不要编造**：项目做什么、什么算交付完成、有哪些硬约束，只能由项目所有者回答。这时写入带 TODO 的骨架，并把问题一次问清（见第三节）。
- 已经有部分文件时只补缺的：先读已存在的，按需增量改，不重写用户写过的内容。

## 二、写 AGENTS.md

1. 读 `references/conventions.md` 得到约定正文。
2. 读目标项目的 `AGENTS.md`（不存在就视为空）。
3. 把约定正文并入受管区块，保留文件里的其它内容：
   - 区块以 `<!-- dsh-leader-kit:conventions:start -->` 开头、`<!-- dsh-leader-kit:conventions:end -->` 结尾。
   - 已有同区块就整体替换该区块；没有就追加到文件末尾；空文件直接写入区块。

dsh 读取 `AGENTS.md` 作为系统提示段落，写入后立即对模型生效。

## 三、写 LEADER.md

1. 读 `references/LEADER.md`，得到骨架（每节都写着该写什么）。
2. 按项目实际改写：这个项目是什么、职责边界、派工粒度、验收口径、不能破的硬约束。
3. 信息不足时保留骨架里的 TODO，不要用通用道理填满——空话会让 leader 在真正需要判断时仍然没有依据。同时把这三个问题问用户：
   - 这个项目做什么、给谁用，明确不做什么？
   - 什么算一次交付完成（命令、读数、人工检查项）？
   - 有哪些不能破的规则（分支与工作区、构建与发布、依赖与兼容范围）？
4. 写到项目根目录的 `LEADER.md`。已存在就先读再改，保留用户已经写好的部分。

`LEADER.md` 由 dsh-leader-kit 每轮 turn 读一次并注入项目的 leader 会话，改了下一轮就生效。

## 四、写 SLOTS.md

1. 读 `references/SLOTS.md`，得到骨架：frontmatter 声明 `dev` / `review` 两个槽位，正文按 `## <槽位名>` 分节。
2. 按项目需要调整槽位（可以增删，frontmatter 与正文章节要同步）。需要单独的需求讨论角色，再加一节 `## discuss`。
3. 每节写这个项目对这类角色的具体要求：开工前读什么、改动范围、验证方式、审查判据。不写通用道理。
4. 写到项目根目录的 `SLOTS.md`。已存在就先读再改。

槽位只描述工作方法与人设，不授予工具权限。

## 边界

- 幂等：可以重复执行；`AGENTS.md` 只动受管区块，另外两份文件先读后改。
- **不编造项目事实**：空目录写骨架并提问，不虚构目标、命令与约束。
- 不覆盖用户已写内容；已有内容与骨架冲突时按用户的写，把差异说明白。
- 三份文件都是活文档：项目变化后回来更新，不指望一次写全。
- 初始化不改项目的代码与依赖，也不是发布流程的一部分。
